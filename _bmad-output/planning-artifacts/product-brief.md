# 校园活动积分与文创兑换平台 — 产品简报

> 一句话定位：把「发活动 → 学生参加 → 自动记分/记时长 → 换文创」这条目前散落在微信群、Excel 和纸面上的链路，收进一套可追溯的双账户账本。

## 一、执行摘要

校级活动的组织权分散在各学院、社团和班级手里，但积分的解释权和统计权集中在团委。今天这条链路被切成了四段：微信群接龙报名、纸质表签到、Excel 手工算分、线下登记兑换。每换一次工具，数据就断一次；到期末，团委面对的是几份口径不一的 Excel。

本产品要做的不是"再做一个报名表"，而是**把一次参与变成两份可追溯的凭证**：一份是能花掉的**积分**，一份是只能累积、不能消费的**志愿时长**。活动申请时就要确定这次活动产出哪一种、面向谁、以及用"只签到"还是"签到 + 签退"来认定完成；报名成功后，小程序在活动开始前 3 小时推送微信通知；到场扫动态签到码，**签到限开始前后 5 分钟、签退限结束前后 5 分钟**；完成情况自动入账并生成流水，学生随时能查"这 5 分是哪场活动给的""这 20 小时志愿时长有没有登记"，积分可以在文创商城兑换，订单 7 天内未核销则自动退分；最后由统计与导出反哺下一轮活动设计。

系统同时用规则约束参与行为：**时间冲突的活动不能同时报名；累计旷活动 3 次后禁止报名 7 天；禁报期内每再旷一次，禁报期顺延 3 天，直到期满才清零重来**。这不是附加功能，而是让"名额"真正落到会来的人手里——一次缺席可以理解，三次缺席就是习惯问题；在禁报期里继续缺席，则说明规则必须能自我加固。

首版面向**计算机与大数据学院 26 级研究生（20 人）**，账号池只放 20 个账号、全部参与，不设第二批试点；系统按 20 人、日常并发 3 / 签到峰值并发 10 设计，跑通后再向其他年级与院系推广。交付目标是一套"微信小程序 + 管理后台"、能完整演示、规则自洽、权限清晰的课程/比赛作品，而不是覆盖全校所有场景的正式平台。

规模小是优势，不是妥协：20 人的完整样本足以暴露规则漏洞，又不至于让冷启动失败归因于"没人用"。时机也合适：团委已经在用 Excel 硬撑，需求是真实的，不是想象出来的；学生对扫码签到、线上核销几乎没有学习成本，推广阻力主要在上游的组织者，而不在用户端。

## 二、问题陈述

**一个真实场景。** 周五晚，某社团办了一场 18 人的讲座。负责人在群里发接龙，现场用纸质表签到，回宿舍后把 18 个名字敲进 Excel，再按"讲座 3 分、竞赛 4 分"的口径逐个算分，发到群里公示。两周后，一名学生来问："我那次志愿活动怎么没记时长？"负责人翻了半小时签到表，才确认是签退时漏了人。期末，团委要把几个社团的 Excel 合并、去重、核对，一个人对了大半天，仍然有学生申诉。

这个场景暴露的不是"缺一个报名工具"，而是五层结构性摩擦：

1. **流程断点。** 报名在群聊、签到在纸表、算分在 Excel、兑换在线下登记本，每换一次载体就丢一次数据，责任也随之模糊；活动临时取消，也只能在群里逐个 @ 人。
2. **凭证不透明。** 学生只看到一个总分，看不到规则、明细和计算依据；志愿时长另记一份 Excel，评优要开证明时找不到依据；组织者凭记忆补录，争议只能靠聊天记录自证。
3. **统计滞后。** 数据在期末才汇总，过程中无法发现"报名 18、到场 9"这类信号，活动运营没有反馈回路。
4. **兑换无闭环。** 文创礼品靠线下纸笔登记，库存、扣分、核销三本账对不上，热门礼品超发、冷门礼品积压都无人察觉。
5. **约束缺失。** 同一时段报两场活动没人拦；报了不来也不承担任何后果，名额被占着，真正想参加的人反而报不上；偶尔缺席和习惯性缺席被同等对待，规则要么不罚，要么一罚就过重。

**根因。** 缺的不是工具数量，而是一条把"参与行为"记成"凭证账户"的主线。没有账本，激励只能靠一次性发放；没有流水，规则就无法被审计，公信力只能靠人背书；没有约束，名额就不是资源。

**代价。** 组织者每场活动多投入 1–2 小时做表格；管理员每学期多投入 1–2 天对账；学生因漏记、错记而对积分体系失去信任；团委拿不到可用于决策的过程数据，也无法向学校证明活动的真实覆盖。

## 四、解决方案

五个环节构成一条闭环，每个环节只解决一件事，但数据必须贯通：

1. **活动申请与审核。** 发布者提交活动：类型（**积分** 或 **志愿时长**，二选一）、面向对象（学院 + 年级）、参与人数上限、时间地点、签到方式（**仅签到** 或 **签到+签退**）、组织凭证/盖章凭证、备注。超级管理员审核活动真实性与分值/时长是否合理，通过后上架。关键设计：**积分活动由发布者在 1–5 分内自选，选到上限 5 分时必须补充说明**（为什么值满分），管理员据此判断是否通过；**志愿活动不填时长**，时长由"签退时间 − 签到时间"自动计算，签退窗口跟随活动结束时间；**组织凭证与盖章凭证必传**，既是审核依据，也是事后追溯的底稿。活动状态分四种：待审核、已发布、已下架、已取消；**发布成功后，发布者可在活动开始前取消并必填原因**，取消即作废、不可恢复。
2. **学生报名与参与。** 浏览、报名、现场扫码签到（按活动配置决定是否还要签退）。报名时做四道校验：面向对象是否匹配、时间是否与已报活动冲突、是否处于旷活动禁报期、名额是否已满；报名成功后，活动开始前 3 小时通过微信订阅消息提醒。关键设计：**签到窗口为活动开始前后 5 分钟，签退窗口为结束前后 5 分钟**，窗口外扫码一律拒绝；**签到码动态刷新，截图与转发无效**。**完成判定由签到方式决定**——"仅签到"的活动签到即完成，"签到+签退"的活动必须两端齐全；**志愿时长类活动强制"签到 + 签退"**，否则无法计算时长。**报名未签到即记一次旷活动，累计满 3 次立即触发 7 天禁报**；禁报只拦新报名，**不影响已经报名的活动**；禁报期内每再旷一次，**禁报期顺延 3 天**；禁报期结束时计数清零。活动被取消时，所有报名记录转为"活动取消"、**不计旷课**，并向全部报名者推送取消通知。
3. **积分/时长核验与发放。** 完成记录确认后，系统按活动类型自动入账：积分活动按发布者选定的分值入账；志愿活动按**签退时间 − 签到时间**计算，**以分钟为最小单位**；窗口关闭后无法签退，记为"已参加但不计时长"。异常情况（**含活动取消后已发放的积分/时长**）支持撤回与冲正。关键设计：每条流水关联活动、名单与规则快照，可回溯到"哪一场、谁确认的、按什么标准"。
4. **文创礼品兑换。** 学生浏览商城、查看积分余额、下单扣分并生成订单；订单有 **7 天有效期**，到期未核销则自动取消并退回积分；核销员扫码核销。关键设计：下单即冻结积分、扣减库存；**到期未核销自动退回积分并回补库存**，两步必须在同一事务内完成，防止超卖与超退。
5. **统计与导出。** 输出参与情况、热门活动、积分消耗、礼品偏好、志愿时长汇总、旷活动与禁报名单；活动表支持导出/打印，用于纸质存档与盖章。可选的排行榜/勋章作为轻量激励。

## 五、差异化

**诚实地说，这里没有技术壁垒。** 壁垒在于对本校流程的贴合度、闭环的完整度，以及数据留在校内。

- **对比微信群 + Excel**：从"事后补账"变成"事中记账"，实时、可查、可审计。
- **对比通用表单/问卷工具**：表单只解决"收集报名"，不解决冲突校验、旷活动累计与禁报、双账户入账、兑换履约与凭证存档。
- **对比现成校园活动平台**（如第二课堂类小程序）：这类平台通常以学分认定为中心、配置较重、由平台方运营，学校只能在其框架内使用；本系统面向校内自办活动与自有文创体系，规则可自定义，礼品可与本校文创绑定。（该判断需在方案对比章节用实际产品核实，不能只凭印象写进答辩材料。）
- **真正的差异点**：**双账户 + 有梯度的约束规则**。大多数"活动报名系统"只记报名，不管"来了没有""该不该让他报""这次给的是分还是时长"；而"累计 3 次才禁报、禁报期内再旷就顺延"这种会自我加固的分级规则，比"缺席即拉黑"更接近真实的学生管理。
- **对课程/比赛项目而言的真实优势**：需求来自真实场景，范围可控，可在有限周期内交付一个完整闭环并演示；20 人的数据量让演示稳定、成本低，也便于逐条核对规则。

不编造：没有独家数据，没有网络效应，也不假设学校会为此单独采购。

## 六、成功度量

分三层看：产品是否真的解决了问题、用户是否愿意用、项目是否交付达标。带"假设"的基线值需在试点中校准。

**北极星指标：每月"完成并成功入账"的活动人次**（有效参与量）。一次参与无论产出积分还是志愿时长，都计 1 人次，两类凭证再分列展示。它同时约束了活动数量与真实到场，避免用"报名数"自欺。

### 产品与运营指标

| 指标 | 现状基线（假设） | 首版目标 |
|---|---|---|
| 单场活动组织者投入（除活动本身外） | 1–2 小时（手工算分、录入） | ≤ 30 分钟 |
| 积分/时长入账时延 | 期末集中处理，延迟数周 | 完成确认后 ≤ 5 分钟 |
| 积分错发/漏发率 | 无统计，估计 5% 以上 | < 1%，且 100% 可追溯 |
| 志愿时长记录完整率 | 依赖个人保存，无法统计 | ≥ 95% 的参与者有可查记录 |
| 期末统计耗时 | 1 人 × 1–2 天 | 报表实时，导出 ≤ 10 分钟 |
| 报名→签到转化率 | 未统计，估计 60–70% | ≥ 80%，且过程可见 |
| 通知触达率（已授权用户） | — | ≥ 90% |
| 窗口内签到完成率 | 未统计 | ≥ 90% |
| 名额浪费率（报名未到场） | 无约束，估计 30–40% | ≤ 20% |
| 订单 7 日核销率 | 无记录 | ≥ 80%，逾期退分 100% 自动 |
| 旷课申诉成立率 | — | < 1%，且处理过程可留痕 |

### 用户指标

- **学生**：首次使用 3 分钟内完成"看活动 → 报名"；积分与时长明细可查；首学期 ≥ 60% 的参与者产生第二次报名。
- **发布者**：≥ 80% 的活动通过系统申请；访谈意愿 ≥ 7/10（愿意下学期继续用）。
- **管理员**：单场活动审核 ≤ 5 分钟；活动表导出打印无需二次加工；期末不再手工合并 Excel。

### 项目验收指标（课程/比赛口径）

- 五条主流程可完整演示，无阻断性缺陷；
- 四类角色权限隔离正确（学生看不到他人积分，发布者只能管自己的活动，核销员只有核销入口）；
- 关键规则可验证：冲突报名被拒；旷活动第 1、2 次只记录、第 3 次立即 7 天禁报且已报名活动不受影响；禁报期内再旷一次、禁报期顺延 3 天；禁报期结束计数归零；积分选 5 分缺说明时无法提交；签到窗口外扫码被拒、过期签到码失效；签退窗口外记为已参加但不计时长；订单过期自动退分并回补库存；重复核销被拒；
- 通知可验证：报名后于活动开始前 3 小时触发一次微信订阅消息，未授权时降级站内信；
- 取消可验证：发布者取消后，报名者收到通知、报名记录转为"活动取消"、不计旷课；开始后取消的，已发凭证被冲正且流水保留；
- 20 人账号池、几十场活动的数据量下，列表与报表响应可接受；
- 交付物齐全：需求、设计、演示脚本、部署说明。

**反指标（防止刷指标）**：不追求活动数量与注册人数；若"积分发放量"上升但"核销率"和"复参率"下降，视为失败信号；若被禁报人数长期超过 3 人（20 人规模的 15%），说明规则设计过严，而不是学生素质差；若活动取消率超过 20%，问题多半在审核或排期，而不在活动本身。

## 七、范围

### 首版做（In Scope）

- 角色与权限：学生、发布者、超级管理员、核销员（核销员仅核销）；
- 客户端：微信小程序（学生、发布者、核销员）+ 管理后台 Web（超级管理员）；
- 活动：申请（类型/对象/人数/时间地点/签到方式/必传凭证/1–5 分/备注）、审核、通过/驳回、上下架、**发布后取消（必填原因，不可恢复）**、状态流转、详情；
- 报名：资格校验（面向对象仅到"学院+年级"、时间冲突、旷活动禁报、名额）、报名/取消；活动取消时批量转为"活动取消"且不计旷课；
- 缺席管理：旷活动累计计数、满 3 次立即 7 天禁报（不影响已报名活动）、禁报期内再旷顺延 3 天、禁报期查询、到期解除并清零、学生申诉入口、管理员受理与撤销（唯一撤销权限）；
- 签到：小程序扫动态码签到，码按时刷新、旧码失效；签到限开始前后 5 分钟、签退限结束前后 5 分钟，窗口外拒绝；志愿类强制签退；
- 双账户：积分发放（1–5 分，5 分需说明）、志愿时长按"签退 − 签到"计算（分钟粒度、窗口外签退不计）、两类流水、余额、撤回/冲正；
- 商城：礼品与库存管理、积分状态、下单冻结积分、7 天订单有效期、到期自动退分、核销；
- 统计与导出：参与/热门/积分消耗/礼品偏好/时长汇总/旷活动名单，活动表导出与打印；
- 通知：微信订阅消息（开始前 3 小时提醒、活动取消通知）、站内消息兜底；

### 明确不做（Out of Scope）

| 不做 | 理由 |
|---|---|
| 在线支付、充值、提现 | 积分是激励凭证而非货币，涉及资金合规与财务对账 |
| 志愿时长兑换文创或折算积分 | 两本账口径不同，折算会破坏认定规则；当前假设时长只记录、不消费 |
| 跨校/多校区/联盟积分 | 首版单学院试点，多组织会引入指数级复杂度 |
| 原生 App 与独立 H5 站点 | 首版以"小程序 + 管理后台"交付，额外维护多端收益低 |
| 闸机、人脸识别、地理围栏签到 | 硬件成本与隐私风险，动态码已能覆盖主要场景 |
| 商家入驻、外部优惠券结算 | 涉及合同与分账，超出"活动—凭证—文创"主线 |
| 社交功能（动态、评论、私信） | 与主线无关，且带来内容审核负担 |
| 智能推荐、算法排课 | 数据量不足以支撑，首版用规则排序即可 |
| 与教务/学籍系统深度对接 | 依赖学校审批与接口排期，首版用名单导入替代 |
| 积分/时长交易、转让、赠送 | 会破坏公平性与可审计性 |
| 候补队列（waitlist）与自动补位 | 需求未提及，先做"满员即止 + 取消释放名额" |
| 按名单精确投放（指定到人） | 首版面向对象只到"学院 + 年级"，名单级投放留到二期 |
| 多级申诉与复核 | 首版只有"学生申诉 + 管理员受理"一层，不做学院—学校两级复核 |
| 信用分、黑名单等更重的处罚 | 3 次禁报 + 顺延已能约束行为，更重的处罚缺乏依据 |
| 活动评价与问卷 | 与凭证发放无直接关系，可二期 |
| 多语言、完整无障碍合规 | 课程/比赛交付不承诺该范围 |

**取舍判据**（后续加需求时用）：不服务于"活动—凭证—兑换"闭环的、需要真实资金流的、需要学校核心系统审批的，一律不进首版。

## 八、关键假设与风险

**假设（需验证）**

- A1 学校允许学生团队以试点方式运行非官方系统，数据可部署在校内或私有服务器。
- A2 目标人群为计算机与大数据学院 26 级研究生（20 人），账号池 20 个且全部参与，日常并发 ≤ 3、签到窗口瞬时并发 ≤ 10。
- A3 积分分值固定为 1–5 分，选 5 分需补充说明并由管理员审核；志愿时长不预设，由签到签退自动计算。
- A4 文创礼品由学校/社团自有，无需与外部供应商结算。
- A5 校园网络环境下扫码签到可用，学生具备智能手机与微信；小程序已完成认证并具备订阅消息能力。
- A6 志愿时长按**实际签到签退差值**计算，精确到分钟；签退窗口关闭后未签退则记为"已参加但不计时长"。
- A7 旷活动判定为"报名后未签到"，主动取消不计入（首版不设请假功能，请假诉求由管理员撤销旷活动处理）；**累计满 3 次立即 7 天禁报，禁报期内再旷一次顺延 3 天，期满计数清零**；学生可申诉，仅管理员可撤销并留痕。
- A8 学生报名时完成订阅授权；未授权、或活动创建时距开始不足 3 小时的，通知降级为站内消息。
- A9 取消仅在活动开始前由发布者发起；开始后只能由管理员处置，且该活动已发放的凭证需冲正。取消只影响本活动，不波及其他活动的凭证。

**风险与应对**

- **R1 代签与刷分** → 动态二维码 + 签到/签退双端 + 同设备多账号异常提示。
- **R2 规则变更引发历史凭证争议** → 规则版本化，流水保存规则快照。
- **R3 禁报误伤**（活动改期、临时取消、签到设备故障导致"被旷课"）→ 管理员可撤销旷课记录并豁免，操作留痕；学生端可见剩余禁报天数。
- **R4 禁报无限顺延**（学生手上有多个已报名活动，反复旷课可把禁报期拖得很长）→ 页面实时显示"再旷一次 +3 天"及顺延后的解除时间；建议单次禁报设总上限（如 30 天），超出转人工处理。
- **R5 订单过期退分的并发问题**（到期瞬间同时核销；首版并发虽低，但定时任务与核销请求仍会撞上）→ 核销与退分加同一把状态锁，过期前先标记"待核销"。
- **R6 冷启动，发布者不愿迁移** → 提供 Excel 导入、一键生成签到码，首场由管理员陪跑。
- **R7 课程周期紧** → 优先保五条主流程，统计只做基础图表。
- **R8 订阅消息触达不稳定**（一次性订阅只能发一条、学生拒收、报名晚于 T−3h）→ 报名成功页引导授权；站内信兜底；活动创建不足 3 小时则创建后立即推送。
- **R9 5 分钟窗口过窄**（现场排队、网络抖动导致签不上）→ 动态码有效期覆盖整个窗口；管理员补签通道，补签单独标记并留痕。
- **R10 小程序审核与类目限制**（个人主体能力受限，正式发布需学校资质）→ 答辩用体验版演示；正式版提前确认主体与类目。
- **R11 订阅消息额度冲突**（T−3h 提醒已消耗一次订阅，活动取消时可能发不出通知）→ 报名时申请多条订阅或改用站内信/短信兜底；取消信息同时置顶在活动详情页。

其余实现细节（凭证合格标准、5 分说明的审核尺度、动态码刷新频率、申诉处理时限）在 PRD 阶段细化，不影响首版范围。

## 九、愿景

**一年内**：让计算机与大数据学院 26 级研究生 20 人全部用起来，学院内大部分活动都走这条链路；"能换文创"成为学生参加活动的一个理由，而不只是评奖需要。

**两到三年**：从"记账工具"长成"校园参与档案"——积分与志愿时长合成一份可导出、可盖章的成长记录，覆盖志愿、社团、竞赛、讲座，在合规前提下与第二课堂学分互认。届时系统回答的不再是"我有多少分"，而是"我在校期间做过什么"。
