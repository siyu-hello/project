### AD-1 — 流水是唯一事实来源，余额由流水派生

- **Binds:** 账本域、商城域、统计；FR-20 ~ FR-23、NFR-3
- **Prevents:** 两处独立维护余额，导致「学生看到的余额」与「可审计的流水」永久漂移
- **Rule:** 任何积分/时长变动必须先写一条不可修改的流水（`入账 / 兑换扣减 / 过期返还 / 冲正`），余额只作为查询结果按公式计算（可物化成缓存列，但必须能由流水重算校验）。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| 直接在 `student.points` 字段上加减，不记流水 | 学生问「这 5 分是哪场活动给的」时答不出来；活动取消要回退时也无从定位；正是 PRD 要消灭的 Excel 现状 |
| 记流水但允许 UPDATE/DELETE 纠错 | 审计链断裂，期末对账无从追责；并发下「读-改-写」会丢失更新；与 NFR-3「账实差异为 0」冲突 |
| 余额与流水双写、以余额为准 | 两个事实来源必然漂移，且一旦漂移无法裁定谁对；对账公式失去意义 |

### AD-2 — 积分与志愿时长双账户分立，时长不可消费

- **Binds:** 账本域、商城域；FR-21、FR-22
- **Prevents:** 时长被折算成积分流入商城，破坏认定规则
- **Rule:** 两个账户各自独立记账（单位分别为「分」与「分钟」），不提供任何换算入口；商城只能扣积分账户；接口层不暴露「时长换积分」的路径。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| 统一积分池，按 1 小时 = X 分折算 | 折算率没有客观依据，吹一次就定死；PRD §6.2 已明确不做，且会让「志愿时长」失去认定含义 |
| 时长不进账本，单独一张表或继续用 Excel | 时长同样要可查、可对账、可冲正；脱离账本就回到「两套记录对不上」的起点 |
| 同一张流水表、共用同一余额字段 | 单位混用后「时长不可消费」在数据层无法保证，只能靠代码自觉 |

### AD-3 — 兑换＝扣减 + 双向流水 + 订单状态锁

- **Binds:** 商城域、账本域；FR-25、FR-26
- **Prevents:** 到期退分与核销并发时出现「双退」「退分未回补库存」
- **Rule:** 下单在同一事务内完成「扣可用积分 → 写兑换扣减流水 → 库存 −1 → 建订单（待核销，`expires_at = now + 7d`）」；到期未核销在同一事务内完成「写过期返还流水 → 库存 +1 → 订单置已过期」；核销与过期对同一订单互斥，靠订单状态的条件更新（`WHERE status = 'pending'`）裁决。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| 冻结模型：拆 `available / frozen` 两列，下单只挪冻结 | 要维护两列恒等式，核销与到期都要回写；等于在账本之外再造一处事实来源，对账更脆 |
| 下单不扣分，核销时才扣 | 学生可无限下单占库存而不付代价，库存被恶意锁死；与「下单即扣减」的产品口径冲突 |
| 到期只改订单状态、不写返还流水 | 退分不可审计，SM-5「逾期返还 100% 自动」无法核验；余额也会与流水总额对不上 |

### AD-4 — 签到码为活动维度动态码，10 秒周期，服务端判定

- **Binds:** 签到模块；FR-13、FR-14
- **Prevents:** 截图转发复用、代签零成本、客户端时钟篡改绕过窗口
- **Rule:** 每场活动一个码空间，码值 = `H(activityId, 周期序号, secret)` 截断为 ≥ 8 位；服务端只接受**当前周期**的码，且以服务端接收时间判定窗口与周期；同一码可被多人使用，同一学生在一场活动内仅允许一条签到记录（唯一约束）。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| 每个学生一个一次性签到码 | 20 人同时到场要逐个出示、逐个核，现场反而更慢；发布者还要二次分发，违背「扫码即签到」 |
| 整场固定静态码（贴一张纸） | 截图与转发立刻可复用，代签成本为零，动态码的安全收益全部丢失 |
| 客户端本地判定窗口与码有效性 | 手机时间可改、页面可离线缓存，绕过成本为零；服务端也无法事后自证 |
| 10 秒周期 + 保留上一周期宽限双窗口 | 等于把「刷新即失效」放宽成 20 秒有效，截图在宽限期内仍可用；与 FR-13 的严格口径冲突（若将来要放宽，需先改 FR-13，而不是在实现里偷偷留窗口） |

### AD-5 — 并发正确性交给数据库：唯一约束 + 条件更新 + 单事务

- **Binds:** 报名、签到、兑换、结算；FR-12、FR-26、NFR-3
- **Prevents:** 最后一名额被两人同时抢到、同一学生重复入账、退分与核销双写
- **Rule:** 名额扣减用条件更新（`UPDATE activity SET enrolled = enrolled + 1 WHERE id = ? AND enrolled < capacity`，影响行数为 0 即失败）；唯一约束承担去重（`(student_id, activity_id)`、`(student_id, activity_id, type)` 的签到/入账、`idempotency_key`）；同一业务动作的单事务不跨服务。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| 应用层单例锁 / `Map` 互斥 | 多进程或重启即失效；锁粒度不可控，长事务会把整个报名串行化 |
| Redis 分布式锁 | 20 人规模为一个锁引入一套中间件，运维与故障面显著增加；且锁失效的场景仍需数据库兜底 |
| 消息队列串行化写操作 | 退化为最终一致，与「下单即扣减、同事务生效」的强一致要求冲突，还要额外解决重复消费 |
| 乐观锁 + 版本号重试循环 | 名额是热点写，重试风暴下不如条件更新直接；版本号还要额外字段与重试逻辑，收益不抵复杂度 |

### AD-6 — 认证授权：小程序 code2session + 后台账密，每请求 RBAC

- **Binds:** 账号与权限；FR-1、FR-2、FR-32
- **Prevents:** 角色被回收后旧 token 仍可用；多角色并集导致的越权面
- **Rule:** 学生/发布者/核销员走微信 `code2session` 换取本系统会话；管理员走后台账号密码（首次强制改密）；一个账号只持有一个角色（FR-32）；每个请求都从库中取当前角色与状态校验，会话短 TTL 且回收即失效。

**被否决的备选方案**

| 备选 | 否决理由 |
|---|---|
| JWT 内嵌角色、签发后不再查库 | 回收角色后 token 到期前仍有效，与 FR-32「回收立即 403」冲突；只能靠极短 TTL 缓解，反而增加登录频次 |
| 学生账号 + 角色位（一人多角色，权限并集） | 已被产品否决（FR-32：学生与发布者是两个独立账号）；且并集权限让「数据范围取交集」难以落地 |
| 管理后台也用微信登录 | 管理员多为老师，绑定与学生同一微信主体不便；后台需要账密 + 锁定策略（FR-1） |
| 仅靠小程序端渲染隐藏菜单 | 接口仍可被直接调用；PRD FR-2 要求接口级 403，隐藏只是体验优化 |
